RED PHONE: written by Claude Code in the cloud session for Red Phone.

field-twin-violet-api is the parts tracker described in the Field Parts Tracker Handoff from October 13, 2026. Red chose the name field-twin-violet-api. It is separate from Field Twin Teal, which is the map tracker at field-twin-teal.vercel.app. All code lives in the GitHub repo sudosilo/field-twin-violet-api on branch ccr-6827ea15-y70t81. Main still holds only the first commit, so the branch has not been merged.

The repo root holds the Railway API. server.js answers GET /, GET /health, and POST /extract. The /extract route takes a base64 photo plus any barcodes the phone already read, sends it to the Anthropic vision model named in VISION_MODEL (default claude-sonnet-5-5), and returns the fields it found with a confidence score for each. Redis caches each result by a hash of the photo for 30 days so the same photo is never billed twice, and it enforces an hourly limit set by EXTRACTS_PER_HOUR (default 150). db.js runs once at boot when DATABASE_URL is set. It creates the tables violet_holders, violet_catalog, and violet_events, along with row level security that lets each user see only their own rows, plus the private storage bucket violet-photos. The Dropbox archive from the first commit was removed in commit f1bf146 because Red never set up Dropbox, and photos now live in Supabase storage.

Railway needs ANTHROPIC_API_KEY, API_TOKEN, REDIS_URL, and DATABASE_URL, and ALLOWED_ORIGINS once the front end address is known. The Railway service address is not known to this session. It is not at field-twin-violet-api-production.up.railway.app or field-twin-violet-api.up.railway.app. Checking /health on the real address shows which of these variables are missing.

The Supabase project is field-twin, ref zasyjjoypkpvyqdueums, shared with Field Twin Teal. All three violet tables, their security rules, and the violet-photos bucket already exist there, which means the Railway service has started at least once with DATABASE_URL set. On October 14 the event log had zero rows. The project has one confirmed user, Red's own login.

The phone app is in the web folder, added in commit 23a728b. It is a multi file installable web app with no build step. The main page is field-twin-violet-v1.html, the code is field-twin-violet-v1.js, the service worker is field-twin-violet-sw.js, and vercel.json routes the site root to the main page. Supabase and the ZXing barcode library are stored in web/vendor so the app works offline. The Supabase URL and publishable key are written into field-twin-violet-v1.js. The app signs in with Supabase email and password. Every save goes into an IndexedDB queue on the phone first, then syncs to Supabase when there is signal. Photos are redrawn on a canvas, which strips location data, and saved as compressed JPEG at 1600 pixels. Barcodes are read on the phone with ZXing, because Firefox for Android has no built in barcode reader. If the API address and token are entered in the app under More, the photo is also sent to /extract. The confirm screen highlights any field read with less than 80 percent confidence, and nothing saves until Red confirms. The app logs received, moved, installed, pulled failed, returned, and written off events. It works out stock per holder from the event log, flags serial conflicts, shows failures counted by part, site, symptom, and cause along with average days installed before failing, exports stock and event history to CSV, and can load invented demo data kept in memory that never touches real records.

The open questions from the original handoff were settled with defaults that Red has not reviewed. Version one tracks only Red's own parts, and the security rules are owner only, so a supervisor role still needs to be added. Symptoms and causes come from a fixed list with an optional note. Parts without serials are counted by quantity per holder. The first clean photo of a part becomes its reference photo, and any later photo can replace it from the catalog screen. Photo location is always stripped. There is no sign up screen, only sign in.

The app was tested in headless Chromium at phone width using demo data. Barcode reading from a photo, the confirm screen, saving, stock, history, failures, conflict flags, CSV export, and adding holders all worked, and a wrong password was rejected by the real Supabase. Saving and syncing to the real Supabase account has never been tested.
